# Site-building workflow audit · 2 October 2026

## Question and conclusion

The owner asked whether 60–70 agents, excessive review, repeated checking and conflicting instructions were creating delay and confusion. The live evidence does not show 60–70 concurrent workers in this task. It does show acceptance gaps, stale instructions and some redundant test coverage. More reviewers alone would not fix them.

- Live collaboration registry at the start: root running, five named reviewers completed. One existing reviewer was reactivated for a bounded read-only code audit and returned a completed report. No new agent was created; no reviewer ran tests, edited code or deployed during this audit.
- The app returned eight pinned and 50 recent threads. Three matched this workspace: `Build Pinnacle verification page (3)` active; `Build Pinnacle verification page (2)` and `Build Pinnacle verification page` idle. This limited listing is not an account-wide exhaustive historical agent count.
- Current project instructions, full governing page work order, active work order, package scripts, Playwright configuration, CI workflow, browser assertions and V163 release evidence.
- Local inventory: 130 files in scripts, 407 in deployment, 86 under reviews and 19 top-level audit directories. These include legitimate historical release/source evidence. File counts do not establish running work, usage cost or waste.
- Recent Git history shows page delivery as well as testing infrastructure and corrective releases. No time/credit breakdown by activity was measured; do not invent a savings percentage.

## Operating rule applied now

1. One main implementation/release owner; normally one read-only reviewer. A second reviewer needs a distinct unresolved issue. No recursive reviewer delegation or one-agent-per-persona committee.
2. One active page brief: family purpose, page-specific narrative, source-backed proof, complete branded creatives, technical/search requirements and the call/enrolment journey. Preserve the full agreed work order.
3. Implement the complete candidate. Consolidate actionable review findings once; resolve or explicitly disposition them. Re-review only affected findings.
4. One local production build per source revision, plus independent CI verification. Reuse accepted assets, unchanged evidence and existing tools. Repeat checks only for a relevant change, failure or distinct execution environment.
5. Inspect the actual changed sections at representative phone/tablet/desktop sizes. For substantive pages, review the full rendered narrative once. Use geometry contracts for layout risks and compare common-shell expectations with the approved baseline.
6. Commit/push, deploy the preserved union and verify production once. Keep cheap byte/route-preservation checks; a page-only edit does not justify repeating every unrelated visual, search and device audit.
7. Close on the defined acceptance criteria, not another round of numerical opinions. Keep one release receipt with source/version, exact checks, screenshot inspection and remaining conditions.
8. If the same question recurs without new evidence, stop repeating it: state the unresolved cause, select one discriminating diagnostic and progress independent work. Do not create more reviewers or reconstruct the entire conversation.

## Testing proportional to the change

- Copy/link/metadata correction: affected content/source assertions and a focused rendered check where wrapping or presentation may change; no automatic full physical-device or Lighthouse run.
- Page layout, artwork or interaction release: active-page checks across 320/390/768/1440, rendered phone/tablet/desktop review, relevant Firefox/WebKit/Edge cases; hosted Safari and representative physical iPhone/Android for actual browser/touch risks. Add iPad or breakpoint/landscape cases when those aspects change.
- Common header/footer/global styles/routing: all affected managed-page integrity checks plus representative page families and shared interaction matrix. Approved baseline stays protected.
- Speed-sensitive images/fonts/layout: one meaningful Lighthouse boundary, with targeted rerun after a relevant repair; keep lab performance separate from field performance.
- Search/distribution: read actual GSC/Bing state when a material publication or measurement interval justifies it. Do not repeat submissions or rebuild the page to fill an unobserved ranking/citation result.
- Documentation-only audit: no site build, visual suite, cloud sessions or deployment.

## Three bounded toolchain improvements still pending

1. Prevent duplicate/superseded CI jobs: branch-aware push/PR policy and concurrency cancellation. Preserve checks on the deployment branch and do not cancel a deployment operation.
2. Select page regressions by changed page/shared dependency; keep PinnacleAI coverage for PinnacleAI or shared-style work. Remove the duplicate generic menu journey while preserving the complete shared helper.
3. Save a small successful CI receipt and representative screenshots, not just failure artifacts. Tie each acceptance result to its exact source revision and environment.

These are not yet implemented in executable scripts. This audit changed project guidance only. No production code, header/footer, deployment, schedule, account route or old task history was changed.
